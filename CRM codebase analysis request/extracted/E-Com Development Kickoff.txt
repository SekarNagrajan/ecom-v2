
Starting the new Solverminds E-Com portal
The process to go from zero to a first shippable module — access and readiness, day-0 bootstrap, environments, the development workflow, and the phased roadmap. This is the "how we work" companion to the hands-on Setup Guide and the per-module Migration Playbook.
The path in one view
Build the reusable platform once, prove it with one read-mostly module end to end, then repeat the Migration Playbook per module. Nothing is a big-bang rewrite; the legacy portal keeps running until each route is switched over.
Access & readiness
Before any code, confirm the team has what it needs:
Git repo + branch permissions; CI provider; a private artifact repository for the backend JARs (no local filesystem paths).
Backend REST facade reachable in dev + its OpenAPI spec URL; auth endpoints (login / refresh) available.
Access to the legacy e-comOnlineWeb_New source (read-only reference) and the CRM shared-ui / theme libs.
Third-party keys where needed: reCAPTCHA, AG Grid Enterprise, payment gateway sandbox (Stripe / N-Genius).
Tooling: Node 24 LTS, pnpm 10, Cursor IDE with the migration .cursor/rules file installed.
Day-0 bootstrap
Follow the Project Setup Guide steps 00–09 to stand up the workspace, shared libs, theme, config, API client, state, auth, and the app shell. Definition of ready to build features:
Nx + pnpm workspace builds; apps/ecom-portal serves the themed app shell.
Login works against the real auth endpoints; a gated route redirects when unauthenticated.
OpenAPI types generate; a sample typed query returns through the shared api client (mock + real).
Lint, typecheck, unit, and one Playwright smoke test run green in CI.
Environments

Env
Purpose

Real REST facade + dev DB; where FE and BE meet per module.
Staging
Production-like; parity checks vs the legacy portal; smoke tests before release.
Production
SPA on CDN + REST facade; modules enabled behind flags, legacy JSP still live for rollback.
Per-env config is Zod-validated; only public values in VITE_*. Secrets stay server-side.
Development workflow
Branch per module/feature off main; one module per PR.
Iterate freely while building; run lint/format/typecheck as a review-and-commit gate, not after every edit.
Conventional Commits (commitlint) — the PR title becomes the squash message and changelog line.
CI runs nx affected lint + typecheck + test + build with a bundle budget.
Cursor is used with the migration rules file + the pinned reference module for consistency.
Every module follows the 12-step Migration Playbook and its Definition of Done before merge.
Delivery roadmap
Team & onboarding
Roles — FE engineers (feature slices), a platform owner (shared libs/theme/api), a BE engineer (REST facade over EJB), QA (parity + e2e).
Onboarding path — read the Architecture Analysis → run the Setup Guide → study the pinned reference module → pick a module and follow the Playbook.
Shared conventions live in AGENTS.md/coding rules + the Cursor rules file so every engineer (and the AI) builds the same way.
Cadence & rituals
Short iterations; a module is the unit of delivery — scope PRs to fit one.
Per-module kickoff: walk the step-01 brief + parity checklist together before building.
Demo each migrated module against the legacy screen at iteration end.
Track migration coverage (routes on React vs JSP) as the primary progress metric toward cutover.
