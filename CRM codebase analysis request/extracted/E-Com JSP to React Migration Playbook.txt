
JSP → React migration — per-module playbook
A repeatable, start-to-finish process for migrating one Struts/JSP module to React using Cursor IDE. Assumes the new project setup is complete. Run the same 12 steps for every module; the rules at the end are non-negotiable.
Principles
Strangler-fig, one module at a time. The legacy Struts app keeps running; each migrated route is switched to the SPA when it reaches parity. Never migrate two modules in one branch.
Reuse the backend. Do not rewrite business logic — expose the existing EJB behind a REST endpoint and consume it. The JSP is a reference for behaviour, not a spec to reinvent.
Parity first, improvements second. Ship an exact functional match, then propose enhancements separately.
Dependency order. Migrate read-mostly modules first (Schedules, Tracking), then transactional (Booking → SI → BL/VGM → Payments), then admin/config.
Definition of done is fixed (see end) — a module isn't "migrated" until every box is ticked.
Cursor IDE workflow
Set Cursor up once so every module migration is consistent and the AI has the right context.
Add a .cursor/rules/ file encoding the project rules (stack, feature blueprint, naming, "no hardcoded styles", RHF+Zod, shared-ui only) — the rules section below is the source.
Open both codebases in the workspace: the legacy e-comOnlineWeb_New (read-only reference) and the new React repo (target).
Use @-mentions to give Cursor the exact JSP + Action + form bean + AJAX servlet for the module, plus one already-migrated module as the pattern to copy.
Work in small, reviewable prompts: analyse → scaffold → one component/hook at a time → wire API → validate. Don't ask it to migrate a whole module in one shot.
Keep the migrated reference module pinned as the canonical example so Cursor mirrors its structure every time.
"Using @Schedules (migrated) as the pattern, scaffold the tracking feature slice. Reference the legacy @Tracking.jsp, @TrackingAction.java, @Tracking.java (ajax). Only scaffold folders + the list route + queryOptions; no UI yet. Follow .cursor/rules."
Module & codebase analysis
Do — inventory everything the module touches before writing any code.
List the JSP page(s), the Struts Action(s), the form bean, and any AJAX servlets for the module (e.g. Tracking → Tracking.jsp · TrackingAction · Tracking ajax).
Map the routes (.do paths + forwards from struts-config.xml) and the module code used by MenuAccess.
Note the user roles that can reach it and any feature flags (GlobalConfig) that alter behaviour.
JSP & backend dependency analysis
Do — trace how the screen gets and saves data.
Follow the Action → EJBLookUp → EJB method calls; record each bean method + its VO/DTO shape.
Identify external calls (schedules, tracking, payment, carbon, mail) and cache reads (ServletContext/Infinispan).
Flag scriptlet logic embedded in the JSP — that hidden business logic must move to the REST layer, not the React component.
UI / UX analysis
Do — capture the screen's structure and every interaction.
Screenshot each state (empty, loading, populated, error, edit). List fields, columns, buttons, modals, tabs.
Map each legacy widget to its Ant Design equivalent (see analysis §19 mapping table).
Record conditional UI (show/hide by role, shipment type E/I, field-config) and the wizard step order if any.
API & business-logic identification
Do — define the REST contract for the module before building UI.
For each EJB method the module needs, add a REST endpoint on the facade with the standard envelope; document it in OpenAPI.
Decide what is a query vs a mutation; keep business rules server-side.
Regenerate FE types from the spec (openapi-typescript) so the module is typed end to end.
React component design
Do — scaffold the feature slice using the standard blueprint.
features/<module>/
├── <module>-list.tsx / -details-view.tsx   # thin route entries
├── api/ .api.ts · .keys.ts · .queries.ts
├── hooks/  use-<module>-controller.ts
├── types/  (generated)  ·  utils/
└── components/  list/  details/  upsert/
Compose from shared-ui only; keep route files thin; put logic in the controller hook.
State & form management
Server data → React Query (queryOptions + staleTime). Client/UI state → Zustand. List filters/sort → URL search params.
Forms → React Hook Form + a Zod schema derived from the legacy validation rules (§18A field-config where applicable).
Wizards → Steps + per-step schema; persist draft in the query cache, not component state.
API integration
Call the module's REST endpoints through the shared api client; never build URLs inline in components.
Wire queries/mutations via the feature's .queries.ts/.keys.ts; invalidate list/detail/summary after mutations.
Develop against MSW mocks first, then switch to the real endpoint; keep both working.
Validation & error handling
Port every Commons Validator + jQuery rule into the Zod schema — match required fields, formats, and cross-field rules exactly.
Surface server errors from the envelope via extractApiError; show inline field errors + a toast for failures.
Wrap the route in an error boundary; handle empty/loading with Skeleton, not blank screens.
Functional parity
Do — verify the React module behaves identically to the JSP one.
Build a parity checklist from the step-01 brief: every field, action, permission, edge case, and message.
Run the same scenario in both apps side by side; diff inputs → outputs (including generated PDFs/Excel).
Confirm role gating and feature-flag behaviour match the legacy MenuAccess rules.
Testing & comparison
Unit: Vitest + RTL for the controller hook and key components; MSW for integration.
E2E: Playwright for the module's critical flow (e.g. create booking, submit SI).
Compare against the legacy module with the same data; log any behavioural difference as a defect, not a "new design".
Code review & quality checks
Run lint + typecheck + format; resolve every warning before review.
PR follows Conventional Commits; one module per PR; link the parity checklist.
Reviewer confirms: blueprint structure, shared-ui usage, no hardcoded styles, no any, no leftover legacy calls, bundle within budget.
Deployment & rollback
Ship behind a feature flag / route switch: the module's routes point to the SPA only when enabled.
Release to staging → smoke test → production; monitor errors and key metrics for the module.
Rollback = flip the route switch back to the legacy JSP (kept live until the module is proven). No redeploy needed.
Decommission the legacy JSP/Action only after a stable soak period with no regressions.
