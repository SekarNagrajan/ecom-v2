
New E-Com project — step-by-step setup
A practical, ordered guide to standing up the new React project on the same platform as the CRM portal — workspace, shared libs, theme, config, API, auth, routing, and the first feature module. Follow the steps top to bottom; each lists its goal, commands, and the definition of done.
React 19 + TypeScript · Ant Design 6 · TanStack Router + Query · Zustand · React Hook Form + Zod · Nx + pnpm + Vite · Vitest + Playwright + Storybook + MSW. Node 24 LTS, pnpm 10.
This guide adds step 13 · Use the @solverminds/shared-ui library covering how to consume the shared component library in the ecom app.
Prerequisites
Goal — a machine that can build the workspace reproducibly.
Node 24 LTS via a version manager (nvm); pin it in .nvmrc.
pnpm 10+ (Corepack: corepack enable).
Git + access to the private artifact repository (for the backend JARs — never local filesystem paths).
Access to the backend OpenAPI spec URL (for type generation) and the CRM shared-ui / theme libs.
Create the workspace
Goal — an empty Nx + pnpm monorepo. Prefer adding to the existing CRM workspace so libs are shared; otherwise create a new one and import the libs.
npx create-nx-workspace@latest solverminds --preset=apps --pm=pnpm
cd solverminds
node -v > .nvmrc            # pin Node
pnpm add -D nx @nx/react @nx/vite @nx/eslint @nx/vitest @nx/playwright @nx/storybook
Apps & shared libs
Goal — the app plus the reusable platform libs. Reuse the CRM libs where they exist; scaffold only what's missing.
pnpm nx g @nx/react:app apps/ecom-portal --bundler=vite --routing=false --style=none
pnpm nx g @nx/react:lib  libs/platform     # api-client, query-client, env
pnpm nx g @nx/react:lib  libs/auth         # store, interceptors, guards, RBAC
pnpm nx g @nx/react:lib  libs/theme        # ConfigProvider, tokens
pnpm nx g @nx/react:lib  libs/shared-ui    # AntD-wrapped components + Form* fields
pnpm nx g @nx/react:lib  libs/shared-util  # dates, formatting, helpers
Add Nx module-boundary tags in each project (scope:ecom, type:feature|ui|util) and enforce with the @nx/enforce-module-boundaries lint rule so features can't import each other.

Auth & guards
Goal — token auth + RBAC replacing the session/systemid model.
Auth store (Zustand): user, in-memory access token, permission set (module codes from RegMenus).
Axios interceptor: attach bearer, 401 → single-flight refresh (httpOnly cookie) → retry.
Login / registration / forgot-password flows + reCAPTCHA v3.

Use the @solverminds/shared-ui library
Goal — consume the existing CRM component library (AppButton, Form* fields, DataView, dialogs, hooks) in the ecom app instead of rebuilding them. The library ships sub-path entry points so heavy deps stay lazy.
Option A — same monorepo (recommended)
Drop libs/shared/ui into the workspace (it already exists as a project). Nx + the @solverminds/source export condition resolve it directly to src/ at dev time — no build step, instant HMR.
// tsconfig.base.json — path mapping (Nx adds this automatically for workspace libs)
"paths": { "@solverminds/shared-ui": ["libs/shared/ui/src/index.ts"] }
// vite.config.mts — resolve the source condition so dev uses src/, not dist/
resolve: { conditions: ['@solverminds/source'] }
Option B — separate repo
If the ecom app lives in its own repo, build the lib (nx build shared-ui → dist/) and publish to your private npm registry, then pnpm add @solverminds/shared-ui. Consumers use the compiled import/types conditions from the same export map. Best kept in one monorepo, though — Option A avoids version-lag.
Import discipline — use the right entry point

Import from
What's inside
@solverminds/shared-ui
Core UI + Form* fields (AppButton, AppModal, AppDrawer, AppTabs, useToast, useConfirm).
…/providers
AppConfigProvider, mergeAppConfig, default config.
…/hooks · …/utils · …/schemas
Reusable hooks, utilities, and Zod schemas.
…/data-view (+ /list-view, /kanban-view, /card-view)
DataView orchestrator + AG Grid views (heavy — separate chunk).
…/chart · …/calendar · …/editor · …/email
ECharts / FullCalendar / Tiptap / email — each behind its own sub-path.
Rule: import light components from the root; import anything that pulls a heavy dep (AG Grid, ECharts, Tiptap, FullCalendar) from its sub-path so the ecom bundle only pays for what a screen uses.
Required wiring (once, at the app root)
Wrap the app in AppConfigProvider (from /providers) inside AntD ConfigProvider + <App> so components read the theme + toast/modal context.
Import the library stylesheet once: import '@solverminds/shared-ui/styles.css' (the lib marks CSS as a side-effect).
Ensure peer deps exist in the app: react, antd, react-hook-form, zod.
For any data-view screen, call initAgGridLicense() once at startup (AG Grid Enterprise key).
import '@solverminds/shared-ui/styles.css'
import { AppButton, FormInput, FormSelect, useToast } from '@solverminds/shared-ui'
import { AppConfigProvider } from '@solverminds/shared-ui/providers'
import { DataView } from '@solverminds/shared-ui/data-view'
 
const form = useForm({ resolver: zodResolver(bookingSchema) })
