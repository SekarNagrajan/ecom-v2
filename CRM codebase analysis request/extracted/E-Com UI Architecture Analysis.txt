
Solverminds ECOM UI — architecture review & new-project blueprint
A source-grounded review of the existing ECOM front-end and a reusable, same-stack architecture blueprint for the next product. Every claim below is traced to a file in the repository; recommendations are separated from findings.
Executive summary
The ECOM portal is a mature, opinionated, modern-React front end built as an Nx monorepo. It separates a single Vite SPA (apps/ecom-portal) from an internal component library (@solverminds/shared-ui). Its conventions are unusually well codified — feature blueprint, API recipe, query-freshness rules, and coding directives are all written down and enforced in CI.
For a fresh product on the same stack, the architecture is largely reusable as a template. The highest-value move is to lift the cross-cutting infrastructure (API client, query client, auth, theme engine, router context) and the shared-ui library into shared libs, then scaffold features with an Nx generator that encodes the existing blueprint. Two areas need attention before reuse: the env / secret handling and the SSE token-in-URL pattern.
Sections 01–16 are the standard analysis. The sections below were added on request to answer specific migration questions and to guide the new build. Related material also lives in two companion files: E-Com Project Setup Guide and E-Com Architecture Diagram.
01Architecture
A client-rendered SPA against a REST backend, organised as a feature-sliced modular monolith. There is no server runtime of its own — Vite emits static assets served behind the tenant subdomain.
Overall shape
EXISTING
Two production projects: apps/ecom-portal (the SPA) and libs/shared/ui (the component library), plus an e2e project and Nx tooling libs.
The source app is multi-tenant/multi-industry (tenant resolved from subdomain in routes/__root.tsx). The new project is single-tenant — that branch is dropped; app config is one static bundle.
~50 feature slices under src/features/, each self-contained and vertically organised.
The React Compiler is enabled for both projects, so manual memoisation is deliberately absent by policy.

04Design system
EXISTING There is no hand-rolled CSS design system. The visual language is a token layer — a pure function (buildAntdTheme) that turns an AppCustomConfig into an Ant Design 6 ThemeConfig, emitted as CSS variables (prefix --sm-*). Components read tokens via theme.useToken(); hardcoded font-size / padding / margin are banned.
Color — default config
These are seeds only — primaryColor is overridden by the app + user config. Surfaces, borders, and text come from a locked light/dark palette pair with identical shape (the type system forces every token to exist in both modes).
Tokens

Typography
System font stack; base 14px (13 on mobile); line-height tight/normal/relaxed = 1.25 / 1.5 / 1.75.
Spacing
Single scale (XXS…XXL) multiplied by a density factor — compact 0.85 / normal 1.0 / comfortable 1.15.
Radius
Global 8px; form controls derive ~75% (≈6px) so dense field rows don't look pill-y.
Control heights
SM 28 / MD 32 / LG 40, rounded-to-even after density scaling.
Components tuned
Per-component overrides for Menu, Button, Card, Form, Segmented, Input, Select, DatePicker, Tabs, Drawer, Modal, Table, Collapse.
Theming & modes
Full light/dark support (plus auto following the OS) via AntD's algorithm swap. Config merges in precedence defaults → app → user through mergeAppConfig; live edits write to the Zustand theme store first (instant feedback) then persist to the backend. Icons come from lucide-react (replacing @ant-design/icons); Tailwind v4 handles utility layout alongside the token system.
The token engine is the crown jewel. It is app-agnostic already — the only thing tying it to this product is its folder location. Lift it verbatim into a libs/theme and both products share one visual language from a single app-level brand config.
05Component architecture
Three tiers, with a clear promotion rule between them. shared-ui is generic and presentational; app/components is cross-feature-but-domain-aware; feature components encode business rules.
Generic primitives with no business logic, split into sub-path entry points so heavy deps aren't paid for unless imported.
App-level shared: layout shell & sidebars, error boundaries, form-section grids, pending skeletons, onboarding wizards, record cards that pull feature data.
Page-specific, split by workflow (list / details / upsert). Encode domain rules — stage colors, conversion flows, capability gating.
Composition & promotion rule
Promote to shared-ui only when a component has no single-feature business logic, is reusable by ≥2 features, and is presentational. This keeps the library clean and is exactly the rule a second product needs.
Deprecated autocomplete kept beside its replacement (see §2).
The blueprint explicitly warns against re-export wrapper components — a sign they have appeared and been cleaned up before; enforce with a lint rule.
DataView's AG-Grid identity constraints are subtle (documented focus-loss bug). Powerful, but a real onboarding cost — keep the docs adjacent to the code.

07State management & data handling
A clean split: React Query owns server state, Zustand owns client state. No Redux, no global store sprawl.
Per-feature queryOptions + local staleTime constants.
Freshness policy codified: lookups 10–30 min, details 30–60 s, lists 15–30 s.
IndexedDB persistence for meta:{persist:true} queries, busted by APP_VERSION.
Record-level optimistic patches; deliberate prefix invalidation after mutations.
Auth store = single source of truth (user, token, permission Set, industry).
Theme/app-config store (instant live theming).
Stores colocated with owning feature; persist middleware → localStorage where needed.
Dual access: getState() in beforeLoad/interceptors, hook in components.
Form & persistence state
Form state is RHF-owned; Zod schemas validate. RHF is skipped for realtime filters/search.
URL is treated as state — list filters/sort live in typed search params (Zod-validated validateSearch).
Client persistence via IndexedDB (query cache) and localStorage (prefs) only — no ad-hoc idb caches inside features (blueprint rule).
This model is correct and modern; reuse it wholesale. The only addition for a template: a documented "when to use URL vs Zustand vs Query" one-pager so new engineers don't reach for a global store by habit.
08API & backend integration
EXISTING A single axios client with interceptor-driven auth, a normalized envelope, and end-to-end type safety from the backend's OpenAPI spec.
Client & interceptors
Request interceptor attaches Bearer from the auth store; withCredentials carries the httpOnly refresh cookie.
Response interceptor handles 401 → refresh → retry with a single-flight refresh queue (concurrent 401s wait on one refresh call), excluding auth endpoints. Refresh failure clears auth and redirects to a session-expired login.
A session-refresh-failed guard short-circuits further protected requests to avoid request storms.
Contract & types
// Stripe/Twilio-style envelope — types/api.types.ts
type ApiResponse<T>      = { data: T; meta?: PageMeta }
type ApiErrorResponse    = { error: { code; message; details? } }
// isApiError() guards · extractApiError() normalizes for UI
 
// Types come from the backend spec, never hand-written:
pnpm generate-types  →  types/generated/api-schema.d.ts
// features reference Schemas['LeadDTO'] etc.
Mock ↔ real live side-by-side in each <feature>.api.ts; a Vite alias (@feature-api) swaps the whole tree in dev-mock mode, so components and hooks contain zero branching. Frontend models map 1:1 to backend DTOs, so a spec change surfaces as a type error, not a runtime bug — this is a deliberate, high-value guardrail.
Reuse the client and envelope as-is. For the template, move mocks behind MSW (network-level) so the same mocks run in dev, tests, and Storybook without a build-time alias — and so mock code can never leak into a prod chunk.
09Routing & navigation
EXISTING File-based TanStack Router with two gate layers and data-loading in beforeLoad.
Code splitting — router plugin auto-splits routes; manual vendor chunks isolate react-dom, luxon, AG Grid, ECharts.
Preloading — intent-based at 200ms hover (tuned to avoid incidental pointer-throughs); stale lazy chunks recover via a preload-error handler.

10Security
The auth model is sound; the risks are concentrated in a few integration seams, not the core.
What's done well STRENGTH
Access token in memory only; refresh via httpOnly cookie — resists XSS token theft better than localStorage tokens.
RBAC as an O(1) permission Set with can/canAll/canAny; route authorization + per-feature capability hooks; server-driven allowed-routes.
Rich-text sanitized with DOMPurify; single-tenant deployment — no cross-tenant data boundary to manage.
SSE token in URL — EventSource can't send headers, so the access token is placed in the notifications URL (logged by proxies/servers). A ticket-based handshake is documented but needs backend work — do it in the template.
Client-side DB creds & crypto — DB passwords and crypto-js keys in the bundle are effectively public. Move all DB access and encryption server-side.
Client-side authz is UX only — permission checks in the SPA must always be re-enforced by the backend (assumed, but state it in the template's security doc).

18Field, module & pipeline configuration
Three configuration systems drive the legacy portal. Each is explained as it works in Struts, then mapped to how we achieve the same capability — cleaner and type-safe — in this React architecture.
A · Field configuration
Admin defines per-field metadata in a FieldConfigVO — fieldCode, searchType, searchValue, inputType, shipmentType (E/I), status. FieldConfigSaveAction persists via EComCntrlBean.saveFieldConfigurationDet; FieldConfigurationView lists it into FIELDCONFIGLIST; JSPs and DynamicColumnSearch read it to decide which fields/columns show and how they render. The metadata lives in the DB but the rendering logic is scattered across JSP scriptlets per screen.
A config-driven form/grid engine. The API serves the same field metadata as typed JSON (GET /field-config?shipmentType=E); the SPA renders from it — no per-screen markup.
A field registry maps inputType → a shared-ui form component (text→FormInput, select→FormSelect, date→FormDatePicker).
A dynamic Zod schema is built from the config (required/visible/type) so validation stays in sync with what admins configured.
The same metadata generates AG Grid column defs (search columns), replacing DynamicColumnSearch.
Cached with React Query (meta:{persist:true}, long staleTime); an admin screen edits it via a normal mutation + invalidation.
// field metadata → UI, one source of truth
const { data: fields } = useQuery(fieldConfigQuery({ shipmentType }))
const schema = buildZodSchema(fields)              // validation from config
const form = useForm({ resolver: zodResolver(schema) })

B · Module configuration
Each .do path maps to a 3-letter module code (BKG, SHI, BOL, VGM, CRO, TRK…) inside MenuAccess. A context map userMenuCategory marks a module "P" (protected); access is granted only if the session's RegMenus list contains the code. Feature toggles live as GlobalConfig key/value rows loaded into ServletContext (e.g. VGMMenuCategory, XSS/analytics flags). The path→code mapping is a giant hardcoded if/else.
Permission set + capability hooks — the granted module codes (today's RegMenus) arrive in the auth payload as a permission set; can('BKG') / useModuleCapabilities() replace the if/else.
Server-driven navigation — the API returns the allowed modules + routes; the sidebar and route guards render from it (no hardcoded path→code table).
Route gates — the app-level beforeLoad authorizes each route against that set, redirecting on miss — replacing the whitelist in processPreprocess.
Feature flags — GlobalConfig becomes typed app config (defaults → app → user), read via useAppConfig(); the backend still re-enforces every check.
C · Pipeline configuration
The shipment pipeline is the stage flow Booking → SI → BL → VGM. CutoffConfig (CutoffConfigVO) defines per-stage deadlines; RequestController tracks progress with session keys WF_ACTIVE_ID/MODULE/STATUS and marks a stage complete when its final submit path (e.g. /SubmitSI.do, /SubmitBL.do) returns 2xx, calling closeModuleStatus on the analytics bean. The stage machine is implicit — spread across the controller, cutoff rows, and the submit actions.
Explicit stage config — the pipeline (stages, order, cutoff rules, allowed transitions) is one typed config from the API, not scattered logic; a workflow feature slice owns it.
Stepper UI — a shared component renders the stage progression from that config; the current stage/status comes from the record via React Query, not session keys.
Cutoff gating — a useStageCapabilities(record) hook derives whether an action is allowed (before cutoff, prior stage complete) and disables the CTA with a reason; the API re-enforces on submit.
Transitions — advancing a stage is a mutation that invalidates the record + list + pipeline-summary queries — the deterministic replacement for the 2xx-based session workflow tracking.
// pipeline as data, gating as a hook
const { stages } = useQuery(pipelineConfigQuery())        // Booking→SI→BL→VGM + cutoffs
const { canAdvance, reason } = useStageCapabilities(record)
<WorkflowStepper stages={stages} current={record.stage} />
<AppButton disabled={!canAdvance} title={reason} onClick={submitStage}>Submit</AppButton>
All three follow the same shift: configuration becomes typed data served by the API and rendered generically on the client — a field registry, a permission/nav set, and a stage machine — instead of DB rows interpreted by scattered JSP scriptlets and controller if/else. The backend remains the source of truth and re-enforces every rule; the SPA just renders and guards from the same contract.

20Login modules & admin configuration
An analysis of how the Struts portal handles logins and why admin configuration (email, module/global, cut-off) is separated — and how to model the same cleanly in React.
How many "login modules"? EXISTING
There are not many auth systems — there are 3 access modes, 3 admin entrypoints, and ~13 login page skins. Distinguishing them is the key insight:

Concept
Count
Detail
Access modes(SESSION_LOGIN_TYPE)
3
U customer/user · V admin/back-office (cpanel/eadmin) · plus a customer-admin variant (sessionAdmin=Y) for multi-customer accounts.
Login entrypoints
4
Customer Accesslogin.do (+ LoginAjax); three admin paths /admin, /cpanel, /eadmin → all one AdminAction → AdminLogin.jsp.
Login page skins
~13
login.jsp, login_A/C/E/F/G/G1/L/M/O/T, login_Mobile, LoginPopup — per-client branding of the same login (all extend .mainloginLayout_new), not separate auth logic.
The ~13 login JSPs are duplicated branding, not distinct features — a maintenance burden. Access mode is a mutable session string set in many places across Accesslogin/LoginAjax, easy to get wrong.
Why admin config is a separate module
Admin configuration screens are gated by AdminMenuAccess, which denies access unless SESSION_LOGIN_TYPE == "V". They all route through /AdminAccess.do?type=…, so they are separated to keep configuration surfaces off the customer session entirely — separation by login type, not by feature domain:
emailtemplate — email configuration (mail alert / templates)
globalConfigAdmin — module / global config (key-value feature flags → ServletContext)
cutoffconfig — cut-off config (per-stage deadlines, §18C)
fieldconfig (§18A) · svrcrestrict (service restriction) · specialprivi (special privilege)
adminreset (password reset) · ImageUploadAdmin · CustomerAdvisoryAdmin
In short: they aren't separate because they're unrelated — they're separated because only the admin (V) login may reach them, and the whole customer portal must never expose a config endpoint.
How to model it in React RECOMMEND
One login flow, not 13 pages — a single themeable login screen; per-client branding comes from tenant/app config (logo, colors), not duplicated JSPs.
Role in the token, not a session string — the JWT carries role (customer / customer-admin / admin) + a permission set; SESSION_LOGIN_TYPE disappears.
Admin as a permission-gated route group — an /admin/* route branch whose beforeLoad requires the admin capability — the typed replacement for AdminMenuAccess.
Config screens as feature slices — features/admin/email-config, .../module-config, .../cutoff-config, .../field-config — same blueprint as any module, gated by capability.
Backend re-enforces — every admin REST endpoint checks the admin role server-side; the client gate is UX only.
// one gate replaces AdminMenuAccess + the login-type checks
export const Route = createFileRoute('/admin')({
  beforeLoad: () => { if (!auth.getState().can('ADMIN')) throw redirect({ to: '/' }) },
})
// admin config screens are ordinary feature slices under /admin/*
